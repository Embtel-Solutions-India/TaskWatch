# ADR-0001: Evolve the existing Express/pg server

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-1, [OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-1, D-18 · all feature areas ([PRODUCT_REQUIREMENTS.md](../../02-product-requirements/PRODUCT_REQUIREMENTS.md))

## Context
- The existing server was built for the previous frontend, deleted on 2026-11-03; the new client runs on a localStorage mock with a different domain model [V-C `client/ASSUMPTIONS.md:3`; [FEATURE_GAP_ANALYSIS.md §5.1–5.2](../../01-discovery/FEATURE_GAP_ANALYSIS.md)].
- The server already implements work-order behaviour that the WO acceptance criteria test: the escalation ladder and routing [V-S `server/src/engine/levels.ts`, `engine/routing.ts`], the notification dispatcher with retries and simulation [V-S `server/src/notify/dispatcher.ts:35-81`], the append-only hash-chained activity log [V-S `server/src/db/migrations/001_init.sql:89-112`, `services/activity.ts:42-156`], Postgres sessions [V-S `server/src/app.ts:31-47`], zod validation and helmet [V-S `server/src/app.ts:23-28`].
- Its stack is existing, observed in code; the reasons it was chosen were never recorded ([README](README.md)).
- Migrations run through a forward-only runner that applies every unapplied `*.sql` file in order [V-S `server/src/db/migrate.ts:8-32`], and the server **applies migrations automatically on start** [V-S `server/src/index.ts:9`].

## Decision
Keep the existing Express 5 / `pg` / zod server and move it to the client's domain model ([`client/src/types/index.ts`](../../../client/src/types/index.ts)) through new forward migrations `002_*.sql` onward. Keep the engine, the dispatcher, the hash-chained activity log, Postgres sessions, zod and helmet. Replace or extend the routes so they serve the client's API operations ([API_CONTRACTS.md](../API_CONTRACTS.md)).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| New server from scratch | Rebuilds tested WO behaviour (ladder, dispatcher, hash chain) for no gain (D-1 option b). |
| Keep the server model, adapt the client to it | The client UI is the approved prototype; the WO says the prototype shows the approved behaviour except where the WO differs [WO p.1]. |

## Consequences
- The schema change is large: see [DATABASE_DESIGN.md](../DATABASE_DESIGN.md). Existing rows must be mapped (statuses, entities, roles); that data migration **needs the D-18 approval** before it is run on `taskwatch` [D-18, decided].
- Because `index.ts:9` migrates on start, simply starting the dev server after `002_*.sql` exists will reshape the dev database. Whoever adds migration 002 must get the D-18 OK first [D-18, decided].
- Old activity-log rows cannot be rewritten (append-only triggers and hashes) [V-S `001_init.sql:104-112`]; new code must read old `kind` and status values and map them at read time ([DATABASE_DESIGN.md §4](../DATABASE_DESIGN.md)).
- Existing server tests (`server/test/*.test.ts`) were written for the old model and were **not executed** during discovery [V-S; EXISTING_SYSTEM_ANALYSIS §3.7]. They must be updated alongside the migrations.
