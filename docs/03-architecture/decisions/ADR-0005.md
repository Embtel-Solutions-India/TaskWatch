# ADR-0005: Due-date changes — extension requests and FR-5 direct change

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-6, [OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-6, D-5 · EXT-01..03, TASK-03, ESC-02

## Context
- WO FR-5: "lead (once), manager or Chief of Staff can extend a due date. The old and new dates and the reason are logged." Past-due rules apply "until the task closes or its due date is extended" [WO p.3].
- Server: direct change `POST /tasks/:id/due` with `dueLocal` and `reason`; permission `extendDue` = cos, manager, or lead while `lead_extension_used` is false [V-S `server/src/routes/tasks.ts:106-111`, `services/access.ts:74`; column `001_init.sql:64`].
- Client: assignee request → overseer approval [V-C `client/src/services/api/tasks.ts:306-345`]; the giver can also change the due date freely through edit [V-C `api/tasks.ts:157-160`].

## Decision
Both paths, each logging old date, new date and reason:
1. **Request/approve (EXT-01..03):** the assignee requests; an overseer with `approve_extensions` (not the requester) decides.
2. **Direct change (FR-5):** an overseer changes the date with a required reason. Allowed for: `cos`; a `manager` overseeing the task; a `lead` overseeing the task **once per task** (`lead_extension_used`). The role test uses `roles[]` (ADR-0004); when a user holds several roles the most senior applies (server `relation()` order cos > manager > lead [V-S `access.ts:37-44`]).
3. The edit form (TASK-03) does not bypass FR-5: a due-date change through edit goes through the same rule.

Every due-date change appends an activity-log row (`due_changed`, before/after) and an `admin_log` audit row, clears the past-due floor and re-evaluates escalation immediately (C-7).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| Request/approve only (D-6 a) | Drops WO FR-5. |
| Direct change only (D-6 b) | Drops the approved UI flow. |

## Consequences
- New `extensions` table; keep `tasks.lead_extension_used` and `original_due_at`.
- Whether approving an assignee's extension counts as the approving lead's single FR-5 change is not stated anywhere; this ADR assumes it does [A] and raises it as D-72 (decided).
- New endpoint `POST /api/tasks/:id/due` (existing, adapted) and the extension endpoints ([API_CONTRACTS.md](../API_CONTRACTS.md)).
- Due-time entry time zone is still [D-5, decided].
