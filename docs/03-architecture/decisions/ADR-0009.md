# ADR-0009: v1 list pagination stays client-side over server-scoped, server-capped results

- **Status:** **Accepted** (2026-11-04, product owner: "accept defaults"; see OPEN_QUESTIONS §9)
- **Date:** 2026-11-03 (proposed)
- **Decided by:** needs approval ([D-10, decided])
- **Related:** D-10, S-17 · TASK-04, TASK-06, AUD-01, DLV-01, NFR Performance

## Context
- The client filters, sorts, pages and exports CSV over the whole list it receives [V-C `client/src/services/api/tasks.ts:18-33`; PRD TASK-04].
- The server applies scope in SQL and caps lists: tasks 500 [V-S `server/src/services/queries.ts:106`], in-app notifications 40 [V-S `server/src/routes/notifications.ts:16`]; no pagination exists (S-17).
- Target volumes are assumptions: see [SCALABILITY_AND_RELIABILITY.md §6](../SCALABILITY_AND_RELIABILITY.md) [A].

## Proposed decision
For v1:
1. List endpoints return the **whole scoped result** up to a server cap, ordered by a stable key, with the response shape `{ items: [...], truncated: boolean }`.
2. Caps [A]: task lists 2 000 rows; audit and delivery logs 2 000 rows inside a required date range (default last 30 days); notifications 200.
3. When `truncated` is true the UI shows "Showing the first N — narrow the filters".
4. Scope is always applied in SQL first (never "fetch all then filter").

## Alternatives considered
| Option | Why not chosen now |
|---|---|
| Server-side keyset pagination now (D-10 b) | Every list page, its filters, sort and CSV export would move to the server; the client is built for client-side tables. Revisit when a cap is hit in practice. |
| No cap | Unbounded responses; S-17. |

## Consequences
- Minimal client change: unwrap `items`, show the truncation notice.
- CSV export over a truncated list is incomplete; exports that must be complete (reports, FR-11 CSV/PDF) are generated on the server.
- Revisit trigger: any production list returning `truncated: true`, or task-list p95 above the NFR target.
