# ADR-0002: Authentication — Google OAuth, email + password, TOTP for senior roles

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-2, D-21, [OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-2, D-21, D-22 · AUTH-01..06, NFR SEC-3, SEC-6, SEC-10

## Context
- The WO requires two-factor authentication for the Manager, Chief of Staff and CEO roles, and server-side access control on every request [WO p.5 "Login"].
- The server today offers Google Workspace OAuth with state, nonce, `email_verified`, domain allow-list, active-directory-user check and session regeneration [V-S `server/src/routes/auth.ts:33-76`], plus a dev directory login outside production [V-S `auth.ts:79-98`, `config.ts:60`].
- The new UI has an email + password form and a reset flow [V-C `client/src/services/api/misc.ts:14-72`], implemented with a shared demo password [V-C `misc.ts:12`] and `Math.random()` reset tokens [V-C `misc.ts:55`, `admin.ts:159`] — both must not reach the backend.
- There is no rate limiting anywhere (S-1) [V-S `server/package.json`].

## Decision
1. **Google Workspace OAuth** stays as is (existing flow). Second factor on this path relies on Workspace 2-Step Verification (D-21).
2. **Email + password** is added:
   - hashing with Node `crypto.scrypt`, a per-user random salt, parameters stored with the hash so they can be raised later;
   - reset tokens from `crypto.randomBytes(32)`, sent only by email, stored only as a SHA-256 hash, single use, 1 h expiry (AUTH-04);
   - sign-in and reset requests are rate-limited and every attempt is recorded ([SECURITY_ARCHITECTURE.md §1, §6](../SECURITY_ARCHITECTURE.md)).
3. **TOTP (RFC 6238)** is mandatory on the password path for any user holding `manager`, `cos` or `ceo` in `roles[]`. It is implemented with Node `crypto` (HMAC-SHA1, 30 s step, 6 digits); **no new dependency**. Secrets are encrypted at rest with a key from the environment.
4. **Dev directory login** stays non-production only (existing guard `config.ts:60`).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| Google only (D-2 option a) | Product owner chose both (D-2). |
| A TOTP or password-hashing library | Node `crypto` covers scrypt, HMAC and random bytes; the project rule is no new library unless necessary. |
| bcrypt/argon2 | Need a native or new dependency; scrypt is in Node. |
| SMS codes | Not requested; adds a provider. |

## Consequences
- New tables `user_credentials`, `password_reset_tokens`, `login_attempts` ([DATABASE_DESIGN.md §3.11](../DATABASE_DESIGN.md)); new env var name for the TOTP encryption key, **Proposed — needs approval** ([SECURITY_ARCHITECTURE.md §1.3](../SECURITY_ARCHITECTURE.md)).
- New UI: TOTP enrolment screen and code step (D-21 notes this).
- Unresolved points raised as new questions: whether the server can rely on Workspace 2SV without verifying it (D-64 (decided)), the lost-authenticator recovery path (D-65 (decided)). See the [SECURITY_ARCHITECTURE.md open items](../SECURITY_ARCHITECTURE.md#12-open-items).
- A user may have both a Google identity and a password; both resolve to the same `users` row by case-insensitive email.
