# ADR-0008: Standalone delivery, not a StatCommand module

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-22, answering WO decision D1; [OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-22, WO-D1, D-2 · AUTH-01, STAFF-01..04

## Context
- The WO recommends building TaskWatch "as a module of StatCommand, sharing its login, user directory and dashboard shell", left as decision D1 [WO p.1, p.7]; its security section assumes "single sign-on with the StatCommand user directory" [WO p.5].
- The repository contains no StatCommand integration; the server has its own `users` directory, sessions and Google sign-in [V-S `server/src/db/migrations/001_init.sql:10-26`, `server/src/routes/auth.ts`]; the SPA is served by the API in production [V-S `server/src/app.ts:65-69`].

## Decision
TaskWatch is a standalone application with its own user directory, its own sign-in (ADR-0002) and its own UI shell. It is deployed as one Node process serving `/api` and the built SPA from the same origin.

## Alternatives considered
| Option | Why not chosen |
|---|---|
| StatCommand module (WO-D1 recommended default) | Product owner chose standalone (D-22). No StatCommand code or API is available in this repo [V-S]. |

## Consequences
- TaskWatch owns user provisioning (STAFF-02) and the 2FA rule for senior roles (ADR-0002) instead of inheriting them from StatCommand.
- The WO's "single sign-on with the StatCommand user directory" is replaced by Google Workspace SSO plus passwords; Google sign-in only admits people already in the TaskWatch directory (existing check `auth.ts:67-68`).
- Same-origin deployment keeps CORS off, which the CSRF design depends on (S-3; [SECURITY_ARCHITECTURE.md §4](../SECURITY_ARCHITECTURE.md)).
