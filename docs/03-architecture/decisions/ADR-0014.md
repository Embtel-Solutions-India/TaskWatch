## 3. Three-clock architecture

| | A. Countdown | B. Deadline escalation | C. Inactivity (silence) |
|---|---|---|---|
| Purpose | Tell the employee how long is left | Hold the hierarchy to the scheduled deadline | Enforce the WO update rhythm |
| Anchored to | `due_at` (fixed) | `due_at` + snapshot delays (fixed timestamps on the task) | `clock_started_at` (moves) |
| Reset by progress / start | **Never** | **Never** | Yes (as today) |
| Reset by | Reschedule (new `due_at`) | Reschedule; reassign with a new due date | Progress, start, reassign, reopen, changes requested |
| Configurable by | Nobody: system constant 10 min | GM (own vertical) and CoS: L2/L3 delay per priority | GM (own vertical, windows/multiples) and CoS |
| Where computed | Server notice (`job_runs`) + client display | `shared/levels.ts` (engine + simulator) | `shared/levels.ts` (unchanged) |
| Output | Notice + floating timer; no level | L1/L2/L3 | L0/L1/L2/L3 |

**Duplicate prevention:**
- B and C stay **independently computed** but share **one delivery path**. The task's level is max(B, C) as today (BR-22).
- The existing unique index means **each level fires once per cycle, whichever clock reaches it first**.
- The escalation's `reason` records the clock that got there first. The activity log records the other clock when it also qualifies. Nobody gets the same level twice.
- The pre-deadline warning is a **notice, not a level**, under its own event type `deadline_warning`. It can never be confused with the silence L0 reminder.

## 4. Deadline escalation algorithm

When a task is published, rescheduled, reassigned with a new due date, or reopened:

```
policy        = effectivePolicy(task.vertical)           // §6, resolved at that moment
[d2, d3]      = policy.deadlineDelaysMinutes[task.priority]
task.deadline_l2_at = due_at + d2                        // stored: fixed timestamps (D-146)
task.deadline_l3_at = due_at + d3
task.policy_version = policy.version
```

On every engine tick (60 s) for each task in a ladder status:

```
deadlineLevel = -1
if now ≥ due_at             → 1
if now ≥ deadline_l2_at     → 2
if now ≥ deadline_l3_at     → 3
silenceLevel  = existing rule (paused while submitted)
blockedLevel  = blocked ? 1 : -1
level         = max(deadlineLevel, silenceLevel, blockedLevel)   // BR-22
fire every level ≤ level not already active (unique index → idempotent)
```

- **Status does not matter.** The task escalates whether it is `assigned`, never started, `in_progress`, `blocked`, `changes_requested` or `submitted` (stakeholder decision: submission does not stop the lifecycle). Only `completed` and `cancelled` stop it.
- **Progress does not matter.** Progress changes only `clock_started_at`, which the deadline clock never reads.
- **Pre-deadline warning:**
  - It fires at `due_at − 10 min`, once per `taskId@dueAt` (`job_runs`). It goes to the assignee by in-app and push, and is skipped once the task is submitted.
  - If the task is assigned less than 10 minutes before it is due, the warning is merged into the assignment notice ("due in 7 min").
- **Start notice:** fires at `start_at − 10 min`, once per `taskId@startAt`, and only when `start_at` is in the future at publish.
- **Catch-up after downtime:** the next tick fires whatever is due, once. `reached_at` records the real threshold time (BR-25).

This is one change inside `computeLevel`: the past-due rule reads the task's stored `[due_at, deadline_l2_at, deadline_l3_at]` instead of `due_at + overdueOffsetsHours`. The simulator passes timestamps computed from the policy, so ADR-0007 parity holds.

## 5. Inactivity monitoring algorithm (unchanged rule, new scope)

- `thresholds[k] = windowsHours[priority] × multiples[k]` for k = 0…3. The values come from the existing configuration (4/24/48/72 h × 1/1.5/2/3); no new values are invented.
- The clock starts at `clock_started_at`, and every reset listed in §1 stays.
- It pauses while `submitted` (D-25).
- L0 (the reminder to the assignee) applies only while the assignee is silent (BR-23).
- **What changes:** a vertical's GM may set its windows and multiples (today only the CoS can, D-48). Nobody can switch the rhythm off, because the WO requires it (D-142).

## 6. Vertical policy inheritance model

Resolution order, **field by field** (leaf level, e.g. `deadlineDelaysMinutes.critical[0]`):

```
effective(vertical) = codeDefaults  ⊕  orgDefault(sla_rules scope 'default')  ⊕  verticalOverride(sla_rules scope = entity id)
```

- **Sparse vertical rows.** A vertical row stores only the fields the GM or CoS changed. Every other field is inherited.
- **Global changes never overwrite customisations.** Changing the org default changes only verticals that inherit that field. Customised fields stay.
- **Fields a vertical may override** (D-142):
  - `windowsHours`
  - `multiples`
  - `deadlineDelaysMinutes`
  - `reviewSlaMinutes`
  - `extraRecipients`
- **Org-wide only (CoS):**
  - `quietHours`
  - `l3NotifyCeo`
  - `ackSnoozeHours`
  - `repeatAfterWindows`
  - `blockedAlertsLead`
  - `dueSoonHours`
- **System constants (nobody edits):** the 10-minute pre-deadline warning and the 10-minute start notice.
- **Versioning:**
  - `sla_rules.version` increases by 1 on every save of that scope.
  - Each save writes an `admin_log` `rules_change` row (already append-only) with scope, version, before, after, actor and note. **That is the policy history.** No new table is needed.
  - The task stores `policy_version` for "which policy governed this escalation".
- **Validation:** see `checkRules`.
  - Delays are whole minutes; L2 ≥ 5 min; L3 > L2; at most 30 days.
  - Review SLA is 5 min – 7 days.
  - Extra recipients must be active members of that vertical or the Founder's Office.

## 8. Default timings (owner-approved 2026-11-12, D-152; a GM may change L2/L3 for their own vertical)

The current behaviour, which is WO-D3 and AC-2, is **L1 at due, L2 at due + 24 h, L3 at due + 72 h for every priority.**

| Priority | Silence windows (unchanged, from config) | **Ship value** (= today, D-152) | **Proposed after sign-off** | Proposed review SLA |
|---|---|---|---|---|
| Critical | 4 / 6 / 8 / 12 h | L2 +24 h, L3 +72 h | **L2 +30 min, L3 +2 h** | 30 min |
| High | 24 / 36 / 48 / 72 h | L2 +24 h, L3 +72 h | **L2 +4 h, L3 +24 h** | 4 h |
| Normal | 48 / 72 / 96 / 144 h | L2 +24 h, L3 +72 h | L2 +24 h, L3 +72 h (unchanged) | 24 h |
| Low | 72 / 108 / 144 / 216 h | L2 +24 h, L3 +72 h | L2 +24 h, L3 +72 h (unchanged; loosening to +48/+120 h is an option) | 48 h |

Rationale for the proposed values:
- **Critical:** the gaps are scaled to its 4 h update window. L2 comes after an eighth of the window (30 min) and L3 after half of it (2 h).
- **High:** L2 comes after a sixth of its 24 h window (4 h) and L3 after one full window (24 h).
- **Normal and Low:** they keep today's WO values, so nothing regresses.

Pre-deadline warning: 10 min for every priority (system constant). The proposed values are set **through the policy UI after approval**, not in code (§18).

## 10. Lifecycle and accountability rules

1. **On time** means `submitted_at` (or `completed_at` without review) ≤ the latest approved `due_at`. This is already how scoring works (`isOnTime`).
2. **Submission does not stop escalation** (stakeholder decision; it matches D-25). It moves accountability:
   - Every escalation row gets `accountable` = `assignee` or `reviewer`.
   - It is `reviewer` when the task was submitted **on time** and is still awaiting review.
   - It stays `assignee` when the submission itself was late. The late levels that already fired remain on the assignee.
3. **Reviewer SLA.** `review_due = submitted_at + reviewSlaMinutes[priority]` (per vertical). R1 and R2 are timed notices (`job_runs`, key `taskId@round@R1/R2`), logged in the activity log. They are **not** L-levels, so they cannot collide with the deadline ladder.
4. **Reports.** Reports and the leaderboard count escalations against whoever is `accountable`. The assignee is never charged for review delay. That is already true for scores (D-125, `isOnTime`); it becomes true for escalation counts too.
5. **Changes requested / rejected.**
   - Accountability returns to the assignee from the decision time. The silence clock restarts (as today).
   - The deadline is unchanged unless the reviewer or giver reschedules it. If it is already past, the task is already escalated and stays so.
   - Proposal: the review dialog offers "set a new due time for the rework", which is the existing FR-5 change, audited.
6. No existing submission or approval rule changes: who may submit, review, approve, the 409 for review-required tasks, and the rounds.

## 12. Database changes (one additive migration, 018)

```sql
alter table tasks
  add column deadline_l2_at          timestamptz,   -- fixed milestones (L1 = due_at)
  add column deadline_l3_at          timestamptz,
  add column policy_version          text,          -- e.g. "default@3,BAIS@2": two scopes can contribute
  add column submission_requirements text;
alter table sla_rules add column version int not null default 1;
alter table escalations add column accountable text not null default 'assignee'
  check (accountable in ('assignee','reviewer'));
-- backfill open tasks with today's offsets → identical behaviour on deploy
update tasks set deadline_l2_at = due_at + interval '24 hours', deadline_l3_at = due_at + interval '72 hours', policy_version = 1
 where status not in ('completed','cancelled');
```

- **No new tables.**
- History lives in `admin_log`.
- Timed notices use `job_runs`.
- Review SLA uses `reviews.submitted_at`.
- `start_at` already exists as `timestamptz`.
- `RulesConfig` JSON gains `deadlineDelaysMinutes`, `reviewSlaMinutes` and `extraRecipients`. Read-time defaults equal today's behaviour, so old rows keep working. `overdueOffsetsHours` is kept for reading and maps to the new field until it is retired.

4. **`engine/engine.ts`:**
   - `sendDueNotices` gains `deadline_warning`, `start_notice`, `review_r1` and `review_r2` (same `job_runs` pattern);
   - `applyLevel` tags `accountable` and adds the reviewer as To while submitted;
   - Critical L1 not quietable (`messages.ts`).
5. **Routes:**
   - `PUT /api/rules/:scope` accepts GM callers;
   - `GET /api/rules/history?scope=`;
   - `POST /api/rules/:scope/apply` (recompute open tasks, audited);
   - `/me` already returns `serverTime` for the countdown.
6. **Safety:**
   - one scheduler (advisory lock);
   - row lock per task;
   - unique active-escalation index;
   - `job_runs` PK for one-shots;
   - everything derived from stored timestamps, so restart-safe and multi-process-safe;
   - no in-memory timers.

## 14. Frontend implementation plan

- **Task form:**
  - Start date **+ time** ("Scheduled start");
  - shows "Duration 1 h 30 min" live;
  - Submission requirements field;
  - Reviewer picker (when review is required);
  - soft warnings for outside working hours and overlap.
- **Floating countdown** (`Shell.tsx`, a new `DeadlineTimer` component):
  - Data comes from the same 60 s poll (SSE later, ADR-0013). Time is `now()` adjusted to server time, never `Date.now()`.
  - **Rule (pure, shared):** take my tasks that are not submitted, closed or draft, with `due − now ≤ 10 min` or already overdue. Show **one** pill for the most urgent: overdue first (the oldest due), then the soonest due.

  - Click opens the task. It can be collapsed to a dot, but an overdue pill cannot be dismissed.
  - Ticks once a second only while visible.
  - `aria-live` announces only state changes (entering the warning, going overdue), not every second; it respects reduced motion.
  - Outside the 10-minute window there is no pill; "My day" shows "Next: X due 1:30 PM".
- **Task detail:**
  - shows "Scheduled 12:00–13:30", a live countdown, and the milestones "L1 13:30 · L2 14:00 · L3 15:30" (the policy version in a tooltip);
  - the next escalation is visible, not only in a tooltip;
  - the accountable party is shown on the escalation history.
- **Dashboards:** the lead's "Today" board (team × scheduled windows, late ones red), review queue with SLA age, and escalation counts split by assignee vs reviewer.

  - field-level merge (a global change keeps vertical customisations);
  - validation bounds;
  - `nextCountdownTask` ordering (overdue first, ties, submitted excluded).
- **Integration** (real HTTP, `taskwatch_test`):
  - GM edits own vertical (200), another vertical (404), the default (403), an org-only field (422);
  - the CoS edits all;
  - version increments with `admin_log` rows;
  - milestones are set on publish, reschedule and reassign, and the D-148 rule is enforced;
  - an open task keeps its milestones after a policy change until "apply";
  - two engine runs send no duplicate escalations or notices; concurrent `applyLevel` is safe;
  - warning, start notice and R1/R2 fire once (`job_runs`);
  - Critical L1 is not held at night;
  - accountability tagging on in-review escalations.
- **E2E** (Playwright + the dev clock): the countdown appears at T−10, turns overdue at T, L1 reaches the lead at T, the GM changes Critical L2 and a new task escalates to the manager at T+30 min, and the policy page shows Inherited/Custom.
- **Update:**
  - TC-ESC-02-01…04 (AC-2 stays green at ship values);
  - TC-ESC-03, TC-ESC-07-01 (due-soon/warning);
  - TC-POL-01…03, TC-POL-02-01 (simulator parity);
  - TC-WF-04-01, TC-WF-06-01, TC-WF-07-01/02, TC-WF-09-01, TC-EXT-02-03.
- **Release gate:** AC-1…AC-10 must stay green.

## 18. Migration and backward compatibility (safest path)

1. **Phase 0.** Approve this ADR and D-140…D-152. Founder's Office signs off D-140/D-152.
2. **Phase 1: no behaviour change.**
   - Migration 018 (additive). Open tasks are backfilled with today's offsets.
   - The shared ladder reads the stored milestones. Policy fields are added with defaults equal to today.
   - The whole test suite plus AC-2 must stay green.
   - Rollback = ignore the new columns.
3. **Phase 2.** Start time, submission requirements, reviewer picker, 10-min warning, start notice, floating countdown.
4. **Phase 3.** Vertical policies: sparse overrides, GM access, versions, history, simulator, "apply to open tasks".
5. **Phase 4.** Reviewer SLA, accountability tagging, report split, Critical quiet-hours exception, D-148 reassign rule.
6. **Phase 5.** The CoS enters the approved default delays **through the policy UI** (audited, versioned; no deploy). Open tasks keep their schedule unless "apply" is used.

Each phase is independently shippable and testable. No data is deleted. Old `overdueOffsetsHours` values are read until Phase 5 replaces them.
