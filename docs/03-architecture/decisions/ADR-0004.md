# ADR-0004: Organization and authorization model

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-4); resolved by the WO (D-8) ([OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-4, D-8, D-18 · STAFF-01..04, ORG-01/02, ROLE-01/02, TASK-04/05, C-2, SEC-1

## Context
- WO: six entities (BAIS, USAIS, International Evaluations, Embtel, Bay Area Accounting Solutions, Founder's Office); "each person sees only the work they own, assigned, or supervise; the Founder's Office sees everything"; reporting lines drive visibility and alert routing; "anyone can be given a second role" [WO p.1–2].
- Server: `entities` table, `users.roles text[]` (⊆ ceo/cos/manager/lead/staff, at least one), `users.manager_id` [V-S `server/src/db/migrations/001_init.sql:4-27`]; authorization hard-coded by role, Founder's Office (`ceo` or `cos`) sees everything [V-S `server/src/services/access.ts:20-26`, `services/directory.ts:90-92`].
- Client: departments → teams [V-C `client/src/types/index.ts:60-71`], a single `role` per user [V-C `types/index.ts:45`], a 15-permission catalogue [V-C `types/index.ts:4-20`], a role × permission matrix in the store [V-C `types/index.ts:376`], defaults in [V-C `client/src/services/mock/seed.ts:47-73`], CoS always has every permission [V-C `client/src/services/authz/permissions.ts:17`, `api/admin.ts:210`], scope from the reporting tree [V-C `permissions.ts:26-39, 64-82`].

## Decision
1. **Department = Entity.** The UI label "Department" becomes "Entity"; the six WO entities are the rows of the existing `entities` table; **teams** sit under entities (new `teams` table). A task's entity comes from its team, else from its assignee (D-4).
2. **Multiple roles per user.** Keep `users.roles text[]`; the client `User.role` becomes `roles: Role[]` (D-8).
3. **Configurable permission matrix in the DB.** New table `role_permissions(role, permission)`. Effective permissions = **union over the user's roles**. `cos` is locked to all 15 permissions: it has no rows, is computed as "all", and the matrix endpoint refuses to edit it (403), as the prototype does.
4. **Scope from the reporting line.** Task visibility, assignable people, people directory and report scope are computed from `manager_id` (transitive reports and ancestors), using the prototype predicates as the reference spec [V-C `permissions.ts`; `workflow.ts:45-73`]. The Founder's Office keeps org-wide visibility: `cos` (all permissions) and `ceo` ("sees all entities, all tasks", read-only by default [WO p.1]) — see D-70 (decided), because the prototype gives the CEO reporting-line scope only.
5. Every check runs on the server for every request, including object-level checks on every `:id` (C-2, SEC-1).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| Keep entities without teams (D-4 option b) | UI is built on teams. |
| Single role + matrix (earlier D-8 recommendation) | WO allows a second role; WO wins. |
| Keep hard-coded role checks | The UI exposes an editable matrix (ROLE-01/02). |

## Consequences
- New tables `teams`, `role_permissions`; new columns `users.team_id`, `entities.head_id` ([DATABASE_DESIGN.md §3.1–3.3](../DATABASE_DESIGN.md)).
- Existing users keep `entity_id` and `roles`; teams must be created and users placed in them. Seeding teams and mapping users is a data change that **needs D-18 approval** [D-18, decided].
- Server `access.ts` role checks are replaced by permission checks; `relation()`'s cos/manager/lead logic remains only where the WO ties a rule to the role itself (FR-5 "lead once", ADR-0005).
- Permission changes take effect on the next request because permissions are read per request ([SECURITY_ARCHITECTURE.md §3](../SECURITY_ARCHITECTURE.md)), fixing the "role changes don't affect live sessions" half of S-9.
- There is no client API to create or rename teams or entities (only `getOrg`, `setTeam` [V-C `client/src/services/api/admin.ts:168-198`]); raised as D-67 (decided).

## Implementation note (2026-11-04, T-1.4)
- The rules live in `shared/permissions.ts`: role and permission lists, the default matrix, `hasPerm` as a union over `roles[]`, the reporting-line scope, visibility, overseer, assignable people, viewing people, and loop detection. IDs are generic, so the server's numbers and the client's strings both work.
- **Decisions applied:**
  - **D-29:** leads lose `reassign_tasks` by default.
  - **D-32:** people who can assign may assign to themselves.
  - **D-33:** the Founder's Office (CoS and CEO) sees everything; the CEO is read-only. Overseers need `create_tasks` to attach files.
- **Tests:** `server/test/permissions.test.ts`.
- **Done 2026-11-04 (T-3.2):** `server/src/services/access.ts` now calls the shared rules. Visibility = `canViewTask` (the SQL filter mirrors it and always includes the caller's organization). Assignable people = shared `assignableUsers` (needs `assign_tasks`). Reassign needs `reassign_tasks`, extend needs `approve_extensions`, posting an update needs `update_assigned_tasks`. Only FR-5's "a lead extends once" still reads the role (`relation`). The Directory carries its organization's role matrix (`dir.org`) and is cleared when the matrix is saved.
- **Still role-based on purpose:** alert routing (WO ladder), the R-1 acknowledgement (CoS), the digest recipients (WO FR-12). Still role-based until their task: people, rules and admin routes (`requireRole`, T-3.4…T-3.7), notifications (T-6), recurring (T-7).
