# ADR-0010: Multiple organizations in one database

- **Status:** Accepted
- **Date:** 2026-11-04
- **Decided by:** Product owner (D-95…D-97 direction; this design and D-100…D-104 approved 2026-11-04)
- **Related:** D-4, D-95, D-96, D-97, D-100…D-104 ([OPEN_QUESTIONS.md](../../01-discovery/OPEN_QUESTIONS.md)) · ADR-0004 (refined, not replaced) · STAFF-*, ORG-*, ROLE-*, SET-01, AUTH-01a, AUD-*, C-2, SEC-1

## Context
- The work order describes one organization: six entities under one Founder's Office [WO p.1].
- D-95…D-97: TaskWatch must hold several organizations in one shared database. Each has its own entities, teams, Chief of Staff, settings, role matrix, escalation rules and audit log. A user belongs to exactly one organization, emails are unique across the platform, and there is no organization picker.
- Today everything is single-organization [V-S]:
  - `entities.id` is a global text key (`'BAIS'`) (`001_init.sql:4`).
  - Settings are one `app_state` row (`services/settings.ts`).
  - The role matrix is one `role_permissions(role, permission)` set (`002_model.sql:31`).
  - SLA rules are keyed `'default'` or by entity id (`001_init.sql:177`).
  - The admin audit log is one global chain whose head is in `app_state` (`005_audit_chain.sql`, `services/audit.ts`).
  - The directory is one cached `Directory` of all users (`services/directory.ts`).
  - Google sign-in checks one platform-wide `GOOGLE_ALLOWED_DOMAINS` (`config.ts:46`).
  - The weekly digest uses one fixed time zone (`config.ts:76`).
- 64 queries in 24 server files read the root tables (tasks, users, entities, teams, recurring tasks, SLA rules, role permissions, admin log, notifications, escalations). Each one needs an organization filter.
- Phase 3 (Org/permissions) builds the parts that become per-organization, so this has to be settled first.

## Decision
1. **An `organizations` table:** `id`, `name`, `active`, `created_at`, `google_domains text[]` and `settings jsonb`. Settings move out of `app_state` and into this row, and only the changed values are stored, as today.
2. **`organization_id` on the root tables:** `users`, `entities`, `teams`, `tasks`, `recurring_tasks`, `sla_rules`, `role_permissions`, `admin_log`, `notifications` and `escalations`.
   - Child tables reach the organization through their parent: `activity_log`, `attachments`, `comments`, `reviews`, `extensions`, `assignments` and `escalation_recipients` through the task; `user_credentials` and `notification_prefs` through the user.
   - **Composite foreign keys** make cross-organization links impossible in the database itself. For example, `tasks(assignee_id, organization_id)` references `users(id, organization_id)`, and the same pattern covers managers, teams and entities. *(D-103: D-95 says "every record carries it". This proposes roots only, with the database guaranteeing the rest.)*
3. **The organization comes from the signed-in user's row,** which `requireUser` already re-reads on every request. It is never taken from the client. Every query filters its root table on that `organization_id`. A `:id` in another organization gets the same 404 as a missing record (the T-1.12 pattern). The directory cache is keyed by organization.
4. **Per organization:**
   - **Role matrix:** `role_permissions` primary key `(organization_id, role, permission)`. The CoS stays locked to all permissions.
   - **SLA rules:** `sla_rules` key `(organization_id, scope)`.
   - **Settings:** `organizations.settings`.
   - **Audit log:** one hash chain per organization. `(organization_id, seq)` is unique, and the chain head is locked per organization. Platform events (an organization created) go on a separate platform chain with `organization_id` null.
   - **Digest time zone:** a setting, defaulting to `Asia/Kolkata`.
5. **Sign-in:**
   - Unchanged: the email finds the user, and the user's row gives the organization.
   - Google sign-in checks the domain against the user's organization's `google_domains`. `GOOGLE_ALLOWED_DOMAINS` becomes a fallback used only when that list is empty (D-101).
6. **Creating organizations (D-100, owner: a UI):** a platform-admin page creates an organization with its first CoS and writes it to the platform audit chain. Platform admins are listed by email in env `PLATFORM_ADMIN_EMAILS` [A: the agent's default, for confirmation]. The page is T-3.9, which is **gated:** it ships only after every reader of the root tables filters by organization (until then only organization 1 exists).
7. **Background jobs** (engine, dispatcher, digest, recurring generation, nightly chain check) loop over the active organizations, with each organization's own settings. The scheduler leader lock stays global.
8. **Migration 007** creates `organizations` and inserts organization 1 (the work order's group; D-104). It adds `organization_id` to the root tables, backfills `1` and sets them `not null`. It moves `app_state.settings` into organization 1 and makes the existing audit chain organization 1's. Before applying it to dev, take a backup and do a dry run on `taskwatch_test` (DATABASE_MIGRATION_POLICY).
9. **Entity codes stay globally unique** (`'BAIS'`). A new organization picks codes that aren't taken (D-102).
10. **`GET /api/me`** adds `organization: { id, name }`. No other client change; there is no picker (D-96).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| A schema or a database per organization | Rejected by D-95 (shared database). Migrations and jobs would run N times. |
| `organization_id` on every table, children included | More columns and more places to forget a filter. Composite foreign keys on the roots give the same guarantee (D-103). |
| Postgres row-level security as the main guard | Needs `SET` on every pooled connection per request, and its failures show up as empty results rather than errors. It could come later as a second layer; application filters plus composite foreign keys plus isolation tests come first. |
| A creation script instead of a UI | Owner chose a UI (D-100). |
| Entity primary key `(organization_id, id)` | Every entity foreign key and the client's string ids would change. Global codes are enough at this scale (D-102). |

## Implementation note (2026-11-04, T-3.0)
- Migration `007_organizations.sql` applied to dev (backup `backups/taskwatch-before-T-3.0-2026-11-04.dump`). Organization 1 is "Vertical" (D-104).
- Per organization now: `getDirectory(org)`, `getSettings(org)`, `getRoleMatrix(org)`, `getRuleSet(org)`, the admin chain (`appendAdmin` derives the chain from the actor; system entries name it), Google domains, `/api/me` `organization`. Every insert into a root table names its organization. Jobs (engine, recurring, digest, chain check) work per organization.
- **Not yet:** list and report readers (`queries.ts`, `reports.ts`, `exports.ts`, the admin audit and outbox views, `GET /entities`) still read every organization. Each phase adds the filter to what it touches (KI-22); T-3.9 waits for all of them. The digest time zone is still the global setting (Notifications phase).
- Test: "Organizations (T-3.0, ADR-0010)" in `api.test.ts` (separate directories, the database refusing cross-organization links, `/me`, assignable people).

## Consequences
- **Phase 3 gains T-3.0, done first:** migration 007, the organization context in `requireUser`, the directory keyed by organization, per-organization settings, role matrix and audit chain, and `/api/me`. T-3.1…T-3.8 are then built organization-aware.
- **Every later phase** adds the organization filter to the queries it touches. Each phase adds cross-organization isolation tests (TC-ORG-ISO-*): a user in organization 2 gets a 404 or an empty result for organization 1's records on every endpoint. This is a new release gate next to AC-6.
- `devLoginAllowed`, CSRF, sessions and rate limits are unchanged.
- **Risk:** one missed filter leaks data between organizations. The mitigations are composite foreign keys for links, one helper for the root-table filter, and isolation tests per endpoint.
- **The pilot is unaffected:** the work order's six entities are organization 1.
