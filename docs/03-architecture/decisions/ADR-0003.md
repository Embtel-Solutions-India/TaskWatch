# ADR-0003: Task state model — WO FR-2 core plus prototype extras

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decided by:** Product owner (D-3, D-20, [OPEN_QUESTIONS.md §7.1](../../01-discovery/OPEN_QUESTIONS.md))
- **Related:** D-3, D-20, D-18 · WF-01..WF-11, TASK-02, ESC-01

## Context
- WO FR-2: "Task states: Open, In progress, Blocked, Done. Marking Blocked requires a reason." Acceptance: "Marking a task Blocked alerts the team lead within 5 minutes." [WO p.3, p.7]
- Server today: `open | in_progress | blocked | done` [V-S `server/src/db/migrations/001_init.sql:55`]. Blocked is set through an assignee update with a required reason, resets the silence clock, and alerts the L1 route (lead) when `blockedAlertsLead` is on [V-S `server/src/services/tasks.ts:111-160`]. Reassignment returns a blocked task to `open` [V-S `services/tasks.ts:236`].
- Client today: `draft, assigned, in_progress, submitted, changes_requested, reopened, completed, cancelled`, no `blocked` [V-C `client/src/types/index.ts:26-35`], transitions in `TRANSITIONS` [V-C `client/src/services/engine/workflow.ts:6-15`].

## Decision
One status set for client and server:

| Status | WO label | Role |
|---|---|---|
| `assigned` | **Open** | WO core |
| `in_progress` | **In progress** | WO core |
| `blocked` | **Blocked** (new in client; reason required, alerts the lead) | WO core |
| `completed` | **Done** | WO core |
| `draft` | — | prototype extra (not assigned, no notifications) |
| `submitted`, `changes_requested` | — | prototype review loop |
| `reopened` | — | prototype extra |
| `cancelled` | — | prototype extra (closed) |

Transitions = the prototype table [V-C `workflow.ts:6-15`] plus `blocked`:
```
draft             → assigned | cancelled
assigned          → in_progress | blocked | completed | cancelled      (completed: R-2)
in_progress       → submitted | completed | blocked | cancelled
blocked           → in_progress | assigned | completed | cancelled  (unblock via start or progress; assigned on reassign; completed: R-2)
submitted         → completed | changes_requested | cancelled
changes_requested → in_progress | blocked | cancelled
reopened          → in_progress | blocked | cancelled
completed         → reopened
cancelled         → (none)
```
`blocked` is in `ACTIVE_STATUSES` (the assignee still owes work, so the silence and past-due ladder keep running) — this matches the server today, whose engine evaluates every task with `status <> 'done'` [V-S `server/src/engine/engine.ts:41`]. Whether that is the intended business rule is raised as D-71 (decided). Reassignment of a blocked task moves it to `assigned` (mirrors `services/tasks.ts:236`). The transition table lives in the shared rules module (ADR-0007, proposed).

## Alternatives considered
| Option | Why not chosen |
|---|---|
| WO four states only | Removes UI features; D-20 says no UI feature is removed. |
| Drop Blocked (D-3 option b) | Deviates from WO FR-2 and an acceptance criterion. |

## Consequences
- `tasks.status` CHECK changes; existing rows map `open→assigned`, `in_progress→in_progress`, `blocked→blocked`, `done→completed`. This rewrites dev data and **needs D-18 approval** [D-18, decided]. Old activity-log rows keep the old values inside their hashed `before/after` JSON and are mapped at read time ([DATABASE_DESIGN.md §4](../DATABASE_DESIGN.md)).
- Client work: add `blocked` to `Status`, `ACTIVE_STATUSES`, `TRANSITIONS`, `allowedActions` (a `block` action for the assignee), labels, and a reason dialog (WF-11).
- Reports and dashboards need a Blocked bucket (WO FR-10 "Blocked" list filter [WO p.4]).

## Implementation note (2026-11-04, T-1.3)
The transition table, `ACTIVE_STATUSES` (which includes `blocked`) and `allowedActions` live in `shared/workflow.ts`. R-2 added Done from `assigned` and `blocked`; `blocked → assigned` covers reassigning a blocked task. Every from → to pair is pinned by `server/test/workflow.test.ts`. The client's `services/engine/workflow.ts` only gathers the facts about the person and task and delegates. A new `block` action is available to the assignee; its UI (button, reason dialog) and API arrive with WF-11 in the task-core phase.
