# ADR-0013: Real-time screen updates (Server-Sent Events)

- **Status:** Accepted (approved by the owner 2026-11-12; not yet implemented)
- **Date:** 2026-11-11
- **Decided by:** Product owner (D-138)
- **Related:** NTF-01, ADR-0001 (build on the existing server), ADR-0012 (Web Push), DEPLOYMENT DP-7, `client/src/app/App.tsx` (60 s refresh)

## Context
Every screen reads the API through TanStack Query. A person's **own** writes refresh their cards at once, but **other people's** changes appear only on the next 60-second refresh, or when the tab becomes visible again (`App.tsx`, marked as a deliberate shortcut needing an ADR). The owner wants every card for every user to update in real time, so that work handed between people (assign → update → review → approve) shows up without waiting.

Web Push (ADR-0012) alerts a person immediately, but it does not refresh the cards on screen. A different client state library (for example Redux) would not help: the browser still has to be told by the server that something changed.

## Options considered
| Option | Verdict |
|---|---|
| Shorter polling (15–20 s) | One-line change, but still not real time, and several times the request load for everyone, every minute, all day. Kept only as the fallback. |
| WebSockets | Two-way, which TaskWatch does not need (all writes already go through the REST API). Needs a library or a hand-written protocol, and its own auth and CSRF handling. |
| **Server-Sent Events (SSE)** | One-way server → browser over ordinary HTTP. Built into every browser (`EventSource`) with automatic reconnect; it sends the session cookie like any other request, so it reuses the existing login and checks. **No new dependency.** |
| A hosted service (Pusher, Ably, …) | A third party would see task metadata and need its own keys and contract. Not worth it for one signal. |

## Decision
1. **One stream per signed-in browser:** `GET /api/events` (`text/event-stream`), behind the same session and organization checks as every other route. Unauthenticated → 401, as usual. Not counted by the rate limiter (one long request, not many short ones).
2. **Only a signal, never data.** An event says *what* changed, not its contents: `{ "kind": "task", "id": 123 }`, `{ "kind": "bell" }` or `{ "kind": "org" }`. The browser then refetches through the normal, permission-checked API. No task titles, names or other PII go down the stream.
3. **Source of signals, one place each (no new call sites in feature code):**
   - **Task changes:** `appendLog` (`services/activity.ts`). Every task write, including the escalation engine's, already appends exactly one evidence row there.
   - **Bell:** `notify()` (`notify/notify.ts`), for the person notified.
   - **Organization structure:** `appendAdmin` for `staff.*`, `vertical.*`, `department.*`, `role.*` and `settings.*` kinds only (not sign-in or sign-out).
4. **Postgres `LISTEN/NOTIFY` carries the signals.** Each source calls `pg_notify('tw_changes', payload)` **inside its own transaction**. Postgres delivers a notification only when that transaction commits and drops it on rollback, so a screen never refetches before the data is there and never hears about a change that did not happen. Each server process holds one dedicated listening connection. This works unchanged with several server instances (DP-7).
5. **Who receives what.** Each process keeps its open streams in memory, keyed by user. A `task` signal goes to every connected person who **can view that task**: the existing `canView` rule (`services/access.ts`, the reporting line), evaluated in memory from the cached directory. The payload carries the task's parties (assignee, assigner, creator, reviewer) and organization, so no query is needed per event. `bell` goes to that person only, and `org` to everyone in that organization.
6. **Client:** one `EventSource` in `App.tsx`, server mode only. On an event, it marks stale the same TanStack Query keys that one's own saves already refresh. Events are **coalesced for about 1 s**, so a burst (for example the engine escalating 30 tasks) causes one refetch, not 30. No screen or design changes.
7. **Safety nets.**
   - The **60 s refresh stays**, as the fallback when the stream is down.
   - On reconnect, the client refetches once, because it may have missed events.
   - A comment line every **25 s** keeps proxies from closing an idle stream.
   - On each heartbeat the server re-checks the session and closes the stream if the person signed out, was deactivated or timed out.
   - The stream closes cleanly on server shutdown.
8. **Limits.**
   - **Connections:** at most 5 open streams per person per process. The oldest is closed first.
   - **Tabs:** one stream per tab. A browser allows about 6 connections per site over HTTP/1.1, so production should serve **HTTP/2** at the proxy, which is standard for HTTPS. Otherwise, many open tabs could starve the app's own requests.
   - **Throttling:** a person's stream drops repeated signals for the same task within 1 s.

## Consequences
- **Hosting:** the reverse proxy must allow long-lived responses and must not buffer them. With nginx, the server sends `X-Accel-Buffering: no` and the timeout must be at least 60 s. DEPLOYMENT.md gains this.
- **One more Postgres connection per server process**, for `LISTEN`.
- **Load:** about one idle connection per open tab, and one small refetch per affected viewer per change. That is lower than polling at the same freshness.
- **Prototype (mock) mode is unchanged:** it already updates instantly through its in-browser store.
- **Tests:**
  - API: a stream receives a signal after a committed task write and nothing after a rolled-back one; a person who cannot see the task receives nothing; 401 without a session; the stream closes after sign-out.
  - Pure: the coalescing.
  - E2E: two browsers, where one assigns and the other's card updates without a reload.
- **No new permission keys, no new dependency, no schema change** (`pg_notify` needs none).
- **Out of scope:** live typing or presence ("who is viewing"), and pushing data down the stream.
